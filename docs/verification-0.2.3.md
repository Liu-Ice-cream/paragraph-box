## 同数据性能对比

以下为重建仓库前的 0.2.2 / 0.2.3 历史测量。新仓库不携带旧提交；重做版本对比需先在本地准备对应基线提交，再将占位符替换为该提交编号：

```powershell
python scripts/benchmark_index.py --compare-ref <本地0.2.2基线提交> --output .cache/benchmark-0.2.3.json
```

1,000 个文件中索引 900 个文件、9,000 个段落。每次请求打开独立 SQLite 连接，计入同步与检索排名，不含 Python 进程启动或 Flow 界面。缓存测试开始前进行一次不计时的刷新，确保所有测量都位于 2 秒有效窗口；共测量 5 次，旧版每次仍正常扫描。记录见 [原始 JSON](benchmark-0.2.3.json)。

- 0.2.2 后续检索中位数 438.3 ms，最大 570.1 ms。
- 0.2.3 有效缓存期间中位数 155.9 ms，最大 240.4 ms，中位数减少约 64%。
- 0.2.3 首次检索 1,449.1 ms，扫描 294.14 ms、读取 659.24 ms、解析与归一化 136.92 ms、数据库操作 79.81 ms；本次主要耗时来自文件读取。
- 0.2.3 重建 1,066.2 ms；缓存到期后增删改、排除变更、重建前后排序与结果一致性检查通过。

旧版首次运行在前，系统文件缓存影响后续初次读取，因此不据首次数据宣称冷启动提速。以上是本机一次人工资料实验，实际资料库和硬盘可能不同。

## 时间与兼容边界

近期扫描记录持久化在 SQLite，Flow 每次启动新的插件进程也可复用；有效期从上次完成扫描计算，复用不延长时间。缓存到期后的下一次搜索检查文件变化，可见更新仍需本次扫描和检索时间。目录、别名、排除规则或大小限制变化立即检查，`--index` 与手动重建不等待缓存到期。

阶段耗时记录包含扫描及处理，不包括打开索引连接、最后写入报告和事务提交、查询排名及响应传输；实时经过时间从设置服务收到请求算起。因此两者可能不同。所有阶段来自实际执行位置，不报告未经测量的完成百分比。动态阶段当前显示于独立设置页，Flow 查询仍按经典同步协议返回结果。

使用真实 0.2.2 和 0.2.3 ZIP 覆盖升级：自定义全角别名、排除规则、13 条结果限制和 1,300,000 字节上限保留，`config.json` 字节不变，SQLite 原文件记录继续使用，ContextData 与结果一致，插件 ID 不变。旧完成记录在首次扫描后补齐新字段；包不含个人配置、索引或运行环境。
