以下为重建仓库前的历史测量。新仓库不携带旧提交；重做版本对比需先在本地准备 0.2.3 基线提交，再替换命令中的占位符。

```powershell
python scripts/benchmark_search.py --compare-ref <本地0.2.3基线提交> --output .cache/benchmark-search-0.2.4.json
```

从本地 Git 提取 0.2.3 引擎，使用相同 SQLite 数据与人工文档快照；1,000 个 Markdown 文件中排除 100 个，实际索引 900 个文件、9,000 个段落。每次请求独立打开数据库，在不计时的刷新后测量 2 秒有效缓存期间的同步、匹配、排序与原有 Flow 结果格式化；新旧顺序交替，每种查询 5 次。不含 Python 进程启动和页面显示。六种查询的分数、排序、段落与完整 Flow JSON 结果均一致，记录见 [原始 JSON](benchmark-search-0.2.4.json)。

## 行为边界

前后文是同一文件解析后的相邻资料段落，可能跨章节，但显示各自章节与行号。每次展开都立即同步索引，并在单一读取事务内验证原命中段落的行号、正文和章节摘要；并发更新不会拼接不同索引快照。修改时间与大小同时不变的内容仍需手动重建。摘要请求避免重复上传全文，不改变普通 Flow ContextData。

试搜时间来自服务实际执行，包括资料准备、同步与提交、SQL 读取、计分及前若干条选择、结果整理和关闭索引资源；不包含 Python 进程启动、网络响应传输和页面绘制。上次索引阶段记录不含最后提交，故两种时间不一定相同。配置格式、SQLite 结构、Flow 分数、结果顺序和动作数据保持兼容。
